## ADR-001 保留 Electron，不迁 Tauri

**背景**：原案 1.2 节提议 Tauri 2.x + Rust。
**决策**：采用 Electron 44 + React 19，宿主层用 TypeScript。
**理由**：
1. 体积与内存的大头是 Python 服务与 AI 模型（GB 级），Electron 运行时开销（约 200MB）占比可忽略，Tauri 的核心卖点在本产品不成立；
2. 宿主层职责是 I/O 编排（进程管理、转发、FFmpeg 命令行调度），无 CPU 密集计算，Rust 无收益；
3. 避免 TS + Rust + Python 三语言栈，每个功能要动三处，迭代速度永久性变慢；
4. Electron 自带固定版本 Chromium，行为可复现；Tauri 依赖系统 WebView2，版本不受控。

## ADR-002 本地环回 TCP 通信（两次修正后的最终版）

**背景**：v1 用 stdin/stdout 行协议（stderr 混日志、缓冲、半行解析脆弱）。设计期两度修正：
1. 否决 Python 侧 `multiprocessing.connection.Listener`——其线协议为 CPython 私有实现，Node 需逆向；
2. 否决 Windows 命名管道——**实测**（2026-09-05 最小复现实验）：Python 以 CRT 文件句柄打开管道客户端时，读线程阻塞读与执行池线程并发写**同一句柄会死锁写方**（20 条消息 0 投递、写调用永久阻塞）。hello 因在读线程启动前写入而偶然成功，随后全部响应静默丢失。

**决策**：
- **Electron 主进程为服务端**：`net` 监听 `127.0.0.1:0`（系统随机分配端口，仅环回绑定，不触发防火墙弹窗）；
- **Python 服务为客户端**（stdlib `socket.create_connection`）：读写使用 `makefile` 生成的两个独立对象，天然支持跨线程并发；
- **分帧**：NDJSON（每行一条 UTF-8 JSON），自定协议；跨平台同一套代码；
- **认证**：spawn 时经 `DRAMACLIP_AUTH_TOKEN` 传入随机 token，Python 首条 `hello` 携带 token 验证（弥补无管道 ACL 的防插队能力）；
- **生命周期**：Electron 先监听 → 再 spawn；Python 崩溃 → 重启 → 重连同一端口，幸存方始终持有套接字。

**协议细节**：见 `03-IPC协议规范.md`。

## ADR-003 代码 100% 全新重写

**背景**：v1 存在结构性质量问题（类型双处定义、死代码、进程管理烂尾、500+ 行巨型组件），修补成本高于重写。
**决策**：v2 全部代码全新编写，禁止从 v1 复制代码块。v1 全量快照封存于 `legacy/v1-electron` 分支与 `backup/` 目录，仅作只读参考。
**例外（知识而非代码）**：v1 调优结论（消重参数区间、打分权重、台词保护区规则）属于实验数据，提炼为 `06-经验参数表.md` 作为新实现的规格输入。

## ADR-004 扁平 monorepo

**决策**：根目录平铺 `desktop/`（Electron+React 项目根）、`service/`（Python 项目根）、`protocol/`（三端契约），不使用 apps/ services/ packages/ 前缀嵌套。`service/dramaclip/` 的内层目录是 Python 包根（import 需要），等价于 `desktop/src/`，各自只保留一层必要嵌套。
**理由**：每类恰好一个，前缀目录是为不存在的规模付费；将来出现第二个应用时一次 `git mv` + workspace 配置变更即可升级，零锁定成本。

## ADR-005 LLM：OpenAI 兼容抽象，云端默认 + 本地端点可切

**背景**：原案 1.2 提议本地小模型（7B/14B）为主。本地推理需 8-16GB 显存并引入 llama.cpp 类重依赖，会拖慢主线且多数目标用户机器不满足。
**决策**：LLM 统一走 OpenAI 兼容 API 抽象（base_url + api_key + model 三元组可配）。默认云端端点（如 DashScope 兼容模式）保证开箱质量；用户可在设置中切换到本地端点（Ollama / LM Studio 均兼容该协议）实现全离线。P2 再评估内置本地模型托管。
**与"本地优先"的关系**：所有媒体处理 100% 本地；LLM 是唯一可选外部依赖，切换本地端点后即完全离线。

## ADR-006 SQLite 由 Python 服务独占

**决策**：数据库文件仅 Python 服务进程读写（单一写入者），Electron 主进程不直接碰数据库，渲染层一律经 RPC 取数。
**理由**：消除两端 schema 漂移与并发写冲突；权限、迁移、备份只在一处实现。

## ADR-007 功能集完整重规划

**决策**：v2 功能范围以《01-技术方案-原案》为准（三层分析引擎、两阶段分析、九种解说模式、字幕渲染引擎、自动遮罩、消重系统、模型管理、系统设置）。v1 独有功能（字幕文案提取工坊、断点续剪、导出历史、AI 标题生成）**不默认纳入**；其中"AI 标题/简介生成""导出历史"列入 P2 后评估 backlog，其余不再迁移。

## ADR-008 字幕预设两层设计

**决策**：
- **内置预设**：`resources/subtitle-presets/*.json`，只读，随应用版本分发，变更走 code review；
- **用户预设**：SQLite `subtitle_presets` 表（P2 预设编辑器启用），记录 `base_preset_id` 派生关系；
- **解析顺序**：用户预设 > 内置预设 > 全局默认。
**理由**：内置预设是产品内容而非用户数据——入库会导致版本更新与用户改动互相覆盖、需要迁移脚本等自找的复杂度。

## ADR-009 数据归属原则

**决策**：
- 随应用分发、跟版本走的**只读内容**（ffmpeg 二进制、字体、内置字幕预设）→ `resources/` 文件；
- 用户运行时产生的**可变数据**（项目、分析结果、编排方案、导出记录、TTS 缓存、用户预设、设置）→ SQLite / 数据目录文件；
- 数据目录由 **Electron 决定**并通过 `DRAMACLIP_DATA_DIR` 环境变量传给 Python：dev = 仓库 `data/`（gitignored），prod = `%APPDATA%/DramaClip`。
