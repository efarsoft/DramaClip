# DramaClip 深度审计报告

> 审计日期：2026-10-12
> 方法：四路并行深度审计（后端架构 / 测试门禁 / 前端契约 / 文档安全）+ 关键结论**主控实测复核**

## 零、先说结论

这是一个**工程质量显著高于同类个人项目**的代码库：mypy strict 137 文件零告警、1442 个测试用例、测试/生产行数比 1.22:1、全仓 `shell=True` 零使用、ffmpeg 全部走参数列表形式。**门禁是真实的，不存在"嘴上说说"。**

真正的问题不是基础不行，而是**三个系统性的"声明—实现"漂移**：

1. **文档声称的契约，比代码实际能保证的强**（行数红线、模式数量、版本号、API Key 保护）
2. **api 层长成了业务引擎**，名义上的 RPC 薄层里长出了字幕编译器和渲染编排器
3. **安全基线高，但凭据与合规声明两个"最后一公里"没落地**

## 二、P0 · 高危（建议本周）

### P0-1 API Key 明文存储，且随备份持续复制 🔴

**证据**：
- `infra/storage/repos/engine_configs.py:10` —— 表含 `api_key` 明文列；`:60`、`:79` 直接写入
- `infra/config.py:35,36,45` —— `asr.api_key` / `tts.api_key` / `llm.api_key` 存入 settings 表
- `infra/storage/db.py:164-166` —— 仅 WAL / foreign_keys / busy_timeout，**全仓 grep `CryptProtectData` / `dpapi` / `Fernet` / `sqlcipher` 零命中**，确认无任何加密
- **加剧因素**：`:23-26` 的 `_row_to_dict()` 是"**附加** `api_key_masked`"而非**替换**明文，明文原样回传渲染层
- **扩散**：`service_app.py:49` 每次启动自动备份，明文随时间复制到 `data/backups/` 下多份备份

**缓解事实（重要）**：`data/` 已被 `.gitignore` 覆盖（`git ls-files data/` = 0），git 历史无数据库文件、无真实密钥（`git log --all -S "sk-"` 仅命中测试桩）。**风险未外泄至仓库。**

**建议**：
1. 立即轮换现存 LLM 密钥（数据库中存有真实密钥，含启用态的那条）
2. 改用 Windows DPAPI（`CryptProtectData`）加密 `api_key` 列
3. `_row_to_dict` 改为**替换**语义而非附加掩码
4. 备份纳入清理与脱敏策略

### P0-2 AI 生成内容标注义务在桌面端完全缺失 🔴

**证据**：
- `README.md:299` 有明确条款：「成片含 AI 合成语音与 AI 生成文案，发布到具体平台时请按当地法规与平台规则自行标注 AI 生成内容」
- `AboutPage.tsx:17-18` 的 `COMPLIANCE` 常量**只涵盖第一段**（素材授权 + 不提供规避原创性检测），第二段缺失
- 全仓 grep `desktop/src` 的「AI 生成」/「标注」→ **零命中**
- `copyTruth.test.ts:316-319` 的合规门禁**只断言单句字符串**，不校验 UI 呈现、不覆盖第二段

**风险**：用户绝大多数时间只看 UI 不看 README。AI 合成语音与 AI 生成文案的标注义务是面向平台发布方的**法定要求**，这一条丢失比第一段更严重。

**建议**：AboutPage 增列 AI 标注提示；把门禁从"断言单句"改为"UI 与 README 声明全文一致"的数组式断言。

## 三、P1 · 门禁漂移与契约失真（改文案/改字段即可，ROI 最高）

### P1-1 README 行数红线过时（3 处）
`README.md:139,239,281` 仍写「300 行 / 60 行」，实际为 **800 / 120**（2026-10-08 放宽，`docs/04:17-18` 已登记）。
建议同步 README，并给文案真值扫描加一条"README 与 docs/04 规约数字必须一致"的断言——**这类漂移正是该扫描该管却没管的**。

### P1-2 真机门禁漏掉一个模式
`scripts/verify_modes.py:63-67` 的 `ALL_MODES` 只有 **9 个**，缺 `highlight_cut`（高光混剪）；而 `README.md:138` 称"把十种模式各跑一部真剧"。代码侧 `api/narration.py:50` 确认 `highlight_cut` 是真实支持的模式。
建议：补齐 `ALL_MODES`，**并把 `len(ALL_MODES) == len(SUPPORTED_MODES)` 做成断言**，让这类漂移在 CI 阶段即暴露。

### P1-3 契约"唯一真相源"名不副实，已漂移 4 处字段
- `protocol/package.json` **无任何 scripts**，全仓 grep codegen 工具零命中 → schema/TS/Python **纯手工三写**
- 契约测试（`contract.test.ts:9-20`、`test_contract_sync.py:38`）**只比对方法名集合**，不校验字段 → 这正是漂移能长期存活的根因
- 已核实漂移：`AsrSegment.source`（TS/Python 有，schema 无）、`ExportJob.duration_s`/`size_bytes`（TS/Python 有，schema 无，且渲染层 6 处在真实读取）、`NarrationPlan.block_reason`（同上）、`PlanMode` 枚举 schema 缺 `highlight_cut`
- `analysis.json:76-82` 内联重复描述了 `AsrSegment`，应为 `$ref`

**讽刺之处**：schema 恰恰是那个"不权威"的一方——它漏了 Python 和 TS 都有的字段。

建议按序：① 补齐 4 处漏字段（10 分钟，立刻止损）② 加字段级契约测试锁住高频方法 ③ 落地 codegen ④ 消除内联重复。

### P1-4 版本号三方不一致
`service/pyproject.toml:7` 是 **0.2.0**，`package.json:4` 与 `desktop/package.json:4` 都是 **0.2.1**。而 `AboutPage.tsx:118` 会把两个版本号**并排展示给用户**。应用版本回退到 0.2.1 是有意的（git log 有据），但**服务版本从未对齐**。

### P1-5 前端任务账三条并存通路
同一"任务账"事实，渲染层有三条互不相通的取数路径：
- **A** `stores/jobs.ts:35` ← JobsFeed 全局轮询（开抽屉 2s / 关 10s）
- **B** `useLibraryFacts.ts:39` ← 自拉 `jobsApi.list`（仅挂载时拉一次）
- **C** `useAnalysisWorkspace.ts:95` ← `analysisApi.status`

**后果**：剧库页阶段灯走 B、剧壳页走 A，刷新节奏不同 → **同一剧在两个页面可能显示不同状态**。且 `useLibraryFacts.ts:22` 自称"任务账"，与 `useDramaFacts.ts:3-4` 注释"JobsFeed 是全局唯一轮询点"**互相矛盾**。

建议：删掉 `useLibraryFacts.ts:39` 改用 store，一处改动消除一条通路。

## 四、P2 · 结构债（路径清晰，不紧急）

### P2-1 api 层越界
`api/export.py:572-745` 是**完整的字幕编译器**（174 行纯函数：ASR 词级裁剪 + 双时钟仿射归一 + ASS 行生成），`:949-1172` 是**渲染编排主流程**（224 行）——这些是纯引擎逻辑，100% 属于 `engines/subtitle/` 与 `engines/exporter/`。
好消息：api 层**零裸 SQL、零 subprocess**，145 处 DB 调用全走 repo 门面，`SerializedConnection` 三层锁设计相当出色。问题不是"越界碰基础设施"，而是"长成了业务引擎"。

### P2-2 Python 侧行数红线无机器约束
`pyproject.toml` 只开了 `E/F/W/I/UP/B/SIM`，**无 `C901`（复杂度）/ `PLR0911`（返回过多）/ 行数门禁**。README 宣称的"300 行红线"在 Python 侧是**纯口头约定**——22 个文件超限，最大 `encoder.py` 1349 行。
建议：开 `C901` + `PLR0912`，或加 `import-linter` 把 `docs/04` 的依赖单向规则工具化。

### P2-3 两处真实的并发缺陷
- `engines/analysis/pause_split.py:150` —— **全项目唯一没有 timeout 的 ffmpeg 调用**，且在逐片段循环里（`transcriber.py:281`），一次损坏 wav 可永久阻塞作业线程
- `engines/vision/runtime.py:232-234` —— `close()` 只 `terminate()` 不 `wait()`，进程变僵尸；`_ensure()` 检测到已退出直接 raise，**新进程永不重拉** → 一次崩溃后视觉轨永久失效直到重启服务
- `service_app.py:103` 只收 `indextts2.shutdown_worker()`，漏了对称存在的 `cosyvoice`（`cosyvoice.py:98-107` 注释明说挂在退出路径）

### P2-4 零测试的运行时模块
`tts_runtime.py`(378 行) 与 `cuda_runtime.py`(167 行) **完全无测试**，且被 api 层直接调用。共 545 行裸奔。

### P2-5 仓库体积
`.git` 133MB，其中 `ffmpeg.exe`(96.8MiB) + `ffprobe.exe`(96.5MiB) 明文入库，无 Git LFS，历史还有多个 3~9MB 遗留对象。另 `.worktrees/` 未纳入 `.gitignore`（实测确认）。

## 五、值得表扬的部分（不要在整改中丢掉）

1. **`copyTruth.test.ts` 是本仓最精彩的工程**：`compactText` 整档匹配破解中文折行绕过、红线词表**断言不含空白**（否则紧凑串永远配不上 → 假绿）、"句中折行探针"走生产路径防夹具自我欺骗、扫描面/词表 `minFiles`/`minPhrases` 防缩水。这类设计说明作者**预演过攻击者会怎么做**。
2. **`infra/ffmpeg/runner.py:103-161`** 是全项目唯一正确的 subprocess 实现：Popen + Timer 杀 + cancel watcher + `finally` 里 kill/wait。另有 9 处绕过它直接 `subprocess.run`，建议收敛。
3. **测试断言强度优秀**：无 `assert True` 式假测试；断言精确到 ffmpeg 参数子串（`"-ss 1.500"`）；夹具注明"真机捕获，勿手改数字"；有反向断言（`assert "crop=" not in joined`）。
4. **安全基线**：全仓 `shell=True` 零使用、ffmpeg 全参数列表、滤镜路径转义（`_escape_filter_path`）实现正确、RPC 76 个方法全显式注册无反射调用、token 用 `randomBytes(32)` 且经环境变量注入（不经 argv，避免 `ps` 窥探）、渲染层零 Node/Electron 违规引用。
5. **`conftest.py:33-62`** 用 weakref 排空作业线程池——作者踩过并发 flaky 坑并做了根治。
6. **提交信息质量极高**，每条都写明"为什么"和"业主实测立案"。
