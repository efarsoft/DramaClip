# 04 · 数据模型

> SQLite schema 与数据目录的权威定义。迁移文件位于 `service/dramaclip/infra/storage/migrations/`，
> 本文件与迁移 SQL 必须同步修改（先改本文，再写迁移）。

## 1. 数据目录布局

由 Electron 决定并通过 `DRAMACLIP_DATA_DIR` 传给 Python（ADR-009）：

```
<数据目录>/
├── data.db                  SQLite 主库（WAL 模式）
├── data.db-wal / -shm
├── models/                  已下载模型（按需下载，不入安装包）
├── cache/                   分析缓存 / TTS 音频缓存
├── outputs/                 导出成片（<project_id>/<安全项目名>_<模式>_<export_id 前 6 位>.mp4）
└── logs/                    服务日志（滚动）
```

| 模式 | 目录 |
|------|------|
| dev | 仓库 `data/`（gitignored） |
| prod | `%APPDATA%/DramaClip`（Windows） |

## 2. 通用约定

- **主键**：TEXT，UUID v4 hex（32 字符）；
- **时间戳**：INTEGER，Unix 毫秒；
- **复杂结构**：JSON 字符串存 TEXT 列（表内注明 JSON）；
- **外键**：显式声明 `REFERENCES ... ON DELETE CASCADE`，连接开启 `PRAGMA foreign_keys=ON`；
- **状态字段**：受控字符串枚举，取值在表定义处注释。

## 3. 表结构（基线 v2 · `001_init`，002~008 新增列以行内注释标注）

### projects —— 项目

```sql
CREATE TABLE projects (
  id          TEXT PRIMARY KEY,
  name        TEXT NOT NULL,
  source_path TEXT NOT NULL UNIQUE,     -- 剧集目录
  status      TEXT NOT NULL DEFAULT 'created',
              -- created | analyzing | ready | exporting
  created_at  INTEGER NOT NULL,
  updated_at  INTEGER NOT NULL,
  cover_path  TEXT,                     -- 项目封面（005 迁移新增）
  settings    TEXT NOT NULL DEFAULT '{}' -- JSON: 项目级参数覆盖（008 迁移新增）
);
```

**`projects.settings` 的线格式（重要）**：库内是 JSON **文本**，但**过 RPC 时是对象**——
`repos/projects.py` 在返回前统一 `json.loads`（`_decoded()`），损坏值与 NULL 一律回退空对象 `{}`。
空对象语义 = 「本项目无覆盖，全部走全局 `settings` 表默认」。这与 `narration_plans.plan_data`
（库内 TEXT / 线上 `PlanData` 对象）是同一套约定，新增 JSON 列一律照此办理，不得把裸文本丢到线上。
写入走 `project.update_settings`：**键级合并**（只动传入的键），某键值为 `null` 表示删除该键（恢复默认）。

### episodes —— 集

```sql
CREATE TABLE episodes (
  id             TEXT PRIMARY KEY,
  project_id     TEXT NOT NULL REFERENCES projects(id) ON DELETE CASCADE,
  episode_number INTEGER NOT NULL,
  source_path    TEXT NOT NULL,
  duration       REAL,                  -- 秒，ffprobe 探测
  status         TEXT NOT NULL DEFAULT 'pending',
                 -- pending | prescreened | analyzing | done | failed
  created_at     INTEGER NOT NULL,
  name           TEXT NOT NULL DEFAULT '', -- 集名（扫描取文件名，006 迁移新增）
  cover_path     TEXT,                  -- 单集封面缩略图（006 迁移新增）
  UNIQUE (project_id, episode_number)
);
CREATE INDEX idx_episodes_project ON episodes(project_id);
```

### episode_prescreen —— 预筛结果（每集一条，轻量）

```sql
CREATE TABLE episode_prescreen (
  episode_id           TEXT PRIMARY KEY REFERENCES episodes(id) ON DELETE CASCADE,
  audio_peak_density   REAL NOT NULL,   -- 音频能量峰值密度
  scene_cut_density    REAL NOT NULL,   -- 场景切换密度
  voice_activity_ratio REAL NOT NULL,   -- 人声活跃度
  motion_intensity     REAL NOT NULL,   -- 画面运动幅度
  prescreen_score      REAL NOT NULL,   -- 加权综合分 0-100
  recommended          INTEGER NOT NULL,-- score >= 阈值(默认70)
  created_at           INTEGER NOT NULL
);
```

### episode_analysis —— 精准分析结果（仅被选中的集）

```sql
CREATE TABLE episode_analysis (
  id              TEXT PRIMARY KEY,
  episode_id      TEXT NOT NULL UNIQUE REFERENCES episodes(id) ON DELETE CASCADE,
  asr_segments    TEXT NOT NULL,        -- JSON: [{start,end,text,speaker?,emotion?}]
  scene_data      TEXT,                 -- JSON: 场景切割 [{start,end}]
  audio_features  TEXT,                 -- JSON: 能量曲线/静音比/语音区/BPM（002 迁移新增）
  conflict_scores TEXT,                 -- JSON: LLM 冲突打分（W3）
  highlights      TEXT,                 -- JSON: 高光片段（W3）
  genre           TEXT,                 -- 题材标签（W3）
  characters      TEXT,                 -- JSON: [{name,role,relations}]（W3）
  analyzed_at     INTEGER NOT NULL
);
```

### narration_plans —— 跨集编排方案

```sql
CREATE TABLE narration_plans (
  id              TEXT PRIMARY KEY,
  project_id      TEXT NOT NULL REFERENCES projects(id) ON DELETE CASCADE,
  narration_mode  TEXT NOT NULL,        -- 九种模式枚举值
  episode_ids     TEXT NOT NULL,        -- JSON: string[]
  plan_data       TEXT NOT NULL,        -- JSON: 编排方案（片段/时间轴/文案/字幕指令）
  tts_segments    TEXT,                 -- JSON: TTS 分段与音频路径
  status          TEXT NOT NULL DEFAULT 'pending',
                  -- pending | generating | ready | failed
  created_at      INTEGER NOT NULL
);
```

### export_jobs —— 导出记录

```sql
CREATE TABLE export_jobs (
  id                 TEXT PRIMARY KEY,
  project_id         TEXT NOT NULL REFERENCES projects(id) ON DELETE CASCADE,
  narration_plan_id  TEXT REFERENCES narration_plans(id),
  narration_mode     TEXT,
  subtitle_preset    TEXT,              -- 内置预设 id 或用户预设 id
  output_path        TEXT,
  status             TEXT NOT NULL DEFAULT 'pending',
                     -- pending | running | completed | failed | cancelled
  progress           REAL NOT NULL DEFAULT 0,
  error              TEXT,              -- 失败原因（004 迁移新增；此前 mark_failed 写不存在的列）
  duration_s         REAL,              -- 成片时长（003 迁移新增）
  size_bytes         INTEGER,           -- 成片大小（003 迁移新增）
  cover_path         TEXT,              -- 逐片钩帧封面（011 迁移新增）
  selfcheck          TEXT,              -- 四项自检成绩单 JSON（015 迁移新增；逐项 pass 三态，
                                        -- null=量不到，宁灰勿假绿；判据与 scripts/verify_modes.py 同源）
  selfcheck_state    TEXT,              -- 汇总态 passed|failed|partial（015；写侧一次算好，
                                        -- 作品库「筛选·自检通过」走等值谓词，零 JSON 解析；NULL=从未自检）
  created_at         INTEGER NOT NULL,
  completed_at       INTEGER
);
```

**维护不变量（启动清扫的前提，改动导出状态机前必读）**：
`exports_repo.reset_stale_pending()` 的谓词是 `status = 'pending'`（写 `status='failed'`、
`error='服务中断'`、**保留 progress**）。它成立依赖一条约束：**当前没有任何代码路径把导出行写成
`running` 或 `cancelled`**（`create()` 落 pending，`_run_export` 只写 completed/failed，
`reset_for_retry` 又复位回 pending）。将来若引入 `running`/`cancelled` 的导出行，该谓词必须同步
放宽为 `status NOT IN ('completed','failed','cancelled')`，否则崩溃残留会重新变成永久排队。
`export.retry` 复位时刻意回到 `pending`（而不是新增一个 running 态）正是为了保住这条不变量：
重试途中再崩一次，该记录仍会被下一次启动清扫正确复位。

> **⚠️ 待人工验证（P-1 出口未闭环，无人跑过）**：崩溃复位链路目前只有自动化证据
> （单测覆盖 `reset_stale_pending` / `sweep_interrupted` / `export.retry` 的 DB 级行为，
> 外加一次性脚本跑通「残留 pending → 清扫 → 两次 retry → `-32405` 且恒 1 行」）。
> **真实进程被杀这一维至今无人执行过**。
>
> 前提说明（决定验证怎么做）：P-1 交付的是**服务端接口**，`jobs.list` / `jobs.get` / `jobs.cancel` /
> `export.retry` / `project.update_settings` 这 5 个方法在桌面端**零调用者**——队列页与「重试」按钮都还没做。
> 因此本步只能在「真实服务 + 数据库」层面验，不能等 UI。
>
> 1. 正常启动桌面应用（Electron 拉起 Python sidecar），挑一个已完成分析的项目发起一次**耗时可见**的导出；
> 2. 进度落在 30%~70% 之间时，用任务管理器**强杀 Python 服务进程**（`dramaclip` / `python` 那个子进程，
>    不是杀 Electron 主程序）；
> 3. 等 Electron 按 restart-policy 自动重启服务（不行就手动重启应用）；
> 4. **先复制再查**（`data/data.db` 是在用的应用库，只读对待）：连 `-wal` / `-shm` 一起复制到临时目录，
>    用任意 SQLite 工具**只读**打开副本执行：
>    `SELECT status, progress, error FROM export_jobs ORDER BY created_at DESC LIMIT 3;`
>    `SELECT type, status, error, label FROM jobs ORDER BY updated_at DESC LIMIT 3;`
>    期望：被杀那条 `export_jobs` 为 `failed / <中断时的进度> / 服务中断`，对应 `jobs` 行同样 `failed`；
>    **绝不能仍是 `pending`**（那就是永久排队，说明启动清扫没跑到）；
> 5. 服务 stdout / `log.append` 通知里出现「恢复上次会话：N 个中断任务、N 个分析中集、N 个未完成导出已复位」
>    ——**三项计数都必须在场**，少一项说明某条清扫漏报；
> 6. UI 侧现状（如实记录，别按想象的队列页去验）：`export.list` 只有前端封装、**没有组件调用它**，
>    作品库走 `export.list_works` 且只返回 `completed` 且有 `output_path` 的记录——
>    因此崩溃那条**在今天的界面上根本看不到**。人工能确认的只有：作品库里**没有**出现那个没渲完的半成品；
>    等队列页（消费 `jobs.list`）上线后，回到此处补验「队列页显示失败而非排队」；
> 7. 再发起一次新导出，确认能正常出片（残留失败记录不阻塞后续导出）。
>
> 验证通过后在此处打勾并记录日期与构建号。

### jobs —— 统一任务表（进度推送与崩溃重入依据）

```sql
CREATE TABLE jobs (
  id         TEXT PRIMARY KEY,
  type       TEXT NOT NULL,
             -- prescreen | analysis | semantic | narration | produce | export | model_download
  ref_id     TEXT,                      -- 关联 project/episode/plan/export/model id
  status     TEXT NOT NULL,
             -- pending | running | completed | failed | cancelled
  progress   REAL NOT NULL DEFAULT 0,
  label      TEXT,                      -- 人读阶段，队列页显示（008 迁移新增）
  error      TEXT,
  created_at INTEGER NOT NULL,
  updated_at INTEGER NOT NULL
);
CREATE INDEX idx_jobs_status ON jobs(status);
```

- **type 取值以代码为准**：上表是 `job_store.create()` 实际创建过的全集。`001_init.sql` 的行内注释
  写了 `tts` 但从未有代码产出该类型，也漏了 `semantic`（`analysis.resync_semantic`）与 `produce`
  （`narration.produce`）；迁移文件不可回改，故此处为准。已知偏差：`protocol/schemas/jobs.json` 的
  `JobInfo.type` 描述同样漏了 `semantic`（type 只声明为 string、无 enum 约束，因此不影响契约测试）。
- **label**：由 `JobStore.set_progress(job_id, percent, label)` 在推进度时顺带写入（分析/导出/配音
  三类长任务已接线），`jobs.list` / `jobs.get` 原样透出为 `JobInfo.label`，可为 NULL。
- **必须 `mark_running`**：启动清扫 `JobStore.sweep_interrupted()` 只扫 `status = 'running'`。
  任何长任务 handler 若不调 `mark_running`，崩溃后该行既不是 running（清不掉）也不是终态，
  会在队列页永久显示排队——`models.download` 踩过这个坑（Task 4 修复），新增任务类型务必照此接线。

### settings —— 全局设置（键值对）

```sql
CREATE TABLE settings (
  key        TEXT PRIMARY KEY,
  value      TEXT NOT NULL,             -- 统一字符串存储，读取侧按类型转换
  updated_at INTEGER NOT NULL
);
```

**初始键清单**（唯一权威源是 `infra/config.py` 的 `DEFAULTS`；`config.load()` 启动时把缺失键按默认值
写进 `settings` 表，因此 DB 里是全量键、用户改动即覆盖该行的值。下表与 `DEFAULTS` 逐项对齐）：

| key | 默认值 | 说明 |
|-----|--------|------|
| `analysis.full_threshold` | `15` | 集数 ≤ 此值跳过预筛直接全量 |
| `analysis.prescreen_threshold` | `70` | 预筛推荐阈值 0-100 |
| `asr.engine` | `faster_whisper` | ASR 引擎（faster_whisper / sensevoice） |
| `asr.model` | `small` | whisper 模型尺寸或本地路径 |
| `asr.device` | `auto` | cpu / auto（auto 走 GPU 需完整 CUDA 库） |
| `asr.language` | `zh` | 转写语言 |
| `subtitle.default_preset` | `conflict-impact` | 全局默认字幕预设 |
| `subtitle.smart_match` | `true` | 情绪智能匹配开关 |
| `llm.base_url` / `llm.api_key` / `llm.model` | 空 | OpenAI 兼容端点三元组（007 迁移会把存量端点搬进 `engine_configs`） |
| `tts.engine` / `tts.voice` | `kokoro` / `zf_001` | 配音引擎与音色 |
| `narration.style_id` | `auto` | 解说风格 |
| `strategy.min_duration_s` / `strategy.max_duration_s` | `30` / `300` | 成片时长区间（编排目标） |
| `download.hf_mirror` / `download.ms_base` | `https://hf-mirror.com` / `https://modelscope.cn` | 模型下载端点（`api/models.py` 的 `endpoints()` 读取） |
| `export.encoder` | `h264` | 编码器 |
| `export.bitrate_kbps` | `8000` | 视频码率 |
| `export.width` / `export.height` | `1080` / `1920` | 输出尺寸 |
| `hardware.max_parallel_jobs` | `2` | 并行任务上限（执行池实际 worker 数 = 此值 + 2，见 `service_app`） |

**两层参数机制（P-1 只落了存储层）**：上表是全局默认（`settings` 表），`projects.settings` 是
**项目级覆盖**层——`project.update_settings` 做键级合并、`null` 值删键恢复默认，设计终态是「读取时
项目覆盖优先于全局」。
> ⚠️ **当前状态**：P-1 交付的是**存储与写入落点**，消费端尚未接线——`projects_repo.get_settings()`
> 目前**零调用者**，渲染/分析读的仍是 `context.settings`（全局）。也就是说现在**设置了覆盖值也不会
> 生效**。接线点在后续阶段（参数面板 + 编排/导出取参处），届时按「项目覆盖 dict 叠加到全局
> Settings 之上」实现，并在本节登记实际使用的覆盖键名。

## 4. 迁移机制

- 迁移文件命名 `NNN_<slug>.sql`（如 `001_init.sql`），**按文件名序号顺序执行**；
- 已执行记录存于 `schema_migrations(name PRIMARY KEY)`；
- 每个迁移整体执行后 `INSERT` 记录并提交；启动时自动跑增量迁移（幂等：已应用即跳过）；
- 禁止修改已合入的迁移文件 —— 变更一律新增 `NNN_xxx.sql`。
