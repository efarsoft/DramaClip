A 案取舍

  • P3/P4/P5/P6 靠结构消解：域内只有一种卡型，生效卡内必有安装态与下载入口。

  • 手感的改动最大：老用户要找「tab」，而 A 案没有 tab。
  • 渲染环节是随应用打包的固定项，放进链条略凑数（可作为常量行处理）。
  • 单页变长；三域同时展开时滚动距离大（靠「收起」缓解）。
  • 与既有 ui-ux-overhaul-plan 的「tab 分组」定案有出入，需同步文案。
  • 改动量最大：EnginesPage.tsx 路由与四 tab 组件重排，约 2 天。

C 案取舍

  • 信息密度与可比性最高；「哪个引擎支持什么」一眼扫完（P10 解得最干净，且天然可排序/筛选）。
  • P1/P2/P6 变成一个列值，写一次就不会跑偏；新增模型只加一行，不加页面。
  • 资产治理动作（校验、修复、释放空间、导入）有了自然归属，P9 常驻而非藏在弹窗。
  • 任务导向最弱：新用户看不出「我该先做什么才能出片」，需要额外一条就绪提示（可补，但会退回 B 的思路）。
  • 1440 宽放 8 列已接近上限；音色选择、参数（device/language/model 档位）这些非资产项必须另找位置（现方案塞进 pill 的「设置」抽屉，多一层）。
  • 表格在桌面端与暗色下最容易显「工程感」，与全站卡片语言偏离最大。
  • 改动量中：新增表组件 + 抽屉，约 1.5 天，但回归面广（键盘/窄窗/长名截断）。

定稿 · 方案 D（本轮实施）已选

按上一节的建议合成：B 的两段式骨架（保留 tab 与深链）＋ A 的开工就绪度（作总览第一块）＋ C 的资产列（合并进资产行，可切列表/表格两种视图）＋ 新增「导入模型」向导（把 P9 从"事后弹窗"变成"入口即校验"）。

导入功能不是锦上添花——它补的是当前唯一的落地缺口：现在放模型只能"人肉拷文件到 models/，再点扫描"，而扫描（models.scan_local）只是重新探测一遍目录，既不搬文件也不判完整性。

先摊开：后端现状的三条事实（决定了体检必须新写判据）
现有实现为什么不够
registry.detect_status()：faster-whisper 只看 snapshots/<hash>/model.bin 在不在；其余引擎更宽——目录树里 rglob 到任一 .bin/.onnx/.safetensors/.pth 就算已装「半条命」判据。下载中断留下一个 model.bin、config 与分片还没落盘 → 判 installed → 引擎加载时才炸。这就是 10 集分析全废的机制，比"缺 refs/main"更准确的说法是判据只看一个文件
models.scan_local()：仅 list_models() 过滤 status=="installed" 并记一条日志无源目录、无搬移、无校验、无冲突处理——名字叫"本地导入"，实际是"重新看一眼"
list_models() 返回体无「引擎是否接入」字段所以 P1 那个硬编码 true 只能由后端补 engine_ready 才能真去掉；前端猜不出来

结论：体检与导入共用同一套新判据（每引擎的必需文件集 + 可选加载试运行），而不是把现有 status 换个皮显示。这也是 D 案唯一必须动后端的部分。
